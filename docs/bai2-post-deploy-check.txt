TÀI LIỆU KIỂM TRA SAU TRIỂN KHAI (POST-DEPLOY CHECK)
===================================================

1. TRÌNH TỰ KIỂM TRA THEO LỚP
- Lớp Hạ tầng: Kiểm tra Docker và file cấu hình (.env, docker-compose.yml) có tồn tại không.
- Lớp Container: Kiểm tra trạng thái Up/Healthy của Nginx và Spring Boot.
- Lớp Ứng dụng: Đọc log Spring Boot để tìm lỗi kết nối DB hoặc lỗi khởi tạo JWT.
- Lớp Người dùng: Truy cập Web cổng 89, thử đăng nhập để kiểm tra luồng gọi API.

2. CÁC CÂU LỆNH SỬ DỤNG
- Xem trạng thái Container: `docker compose ps`
- Xem log Backend: `docker compose logs backend -f`
- Ping thử Healthcheck API: `curl http://localhost:8080/actuator/health`
- Kiểm tra phản hồi Web: `curl -I http://202.92.7.123:89/login.html`

3. 5 NGUYÊN NHÂN LỖI CÓ THỂ GẶP
1. Lỗi 403 Forbidden: Gọi thẳng API mà không đính kèm JWT Token hợp lệ.
2. Backend Crash (Sập): File `.env` thiếu biến `JWT_SECRET` hoặc sai thông tin DB.
3. Site can't be reached: Tường lửa (Firewall) của VPS chưa mở cổng 89.
4. Lỗi 502 Bad Gateway: Nginx chạy tốt nhưng Backend bị sập hoặc đứt mạng nội bộ.
5. Sập VPS do cạn RAM: Thiếu RAM khi chạy `docker compose build` (Lỗi Exit 137).

4. NGUYÊN NHÂN ĐÁNG NGHI NGỜ NHẤT TRONG DỰ ÁN
- Rủi ro lớn nhất là **tạo thủ công file `.env` trên Server**. Điều này làm mất tính "Tự động hóa hoàn toàn" của CI/CD. Nếu chuyển sang Server mới hoặc lỡ xóa file, ứng dụng sẽ sập ngay lập tức vì thiếu cấu hình.

5. 3 VIỆC ƯU TIÊN XỬ LÝ ĐẦU TIÊN
1. Đổi Database: Thay H2 (lưu trên RAM) bằng PostgreSQL/SQL Server có gắn Volume vật lý để không mất dữ liệu giao dịch khi khởi động lại.
2. Khóa kín Backend: Xóa public port 8099, chỉ cho phép Nginx gọi API trong mạng nội bộ để chống tấn công trực tiếp.
3. Cài đặt Cảnh báo: Tích hợp UptimeRobot vào `/actuator/health` để nhận tin báo động ngay khi server có dấu hiệu sập.
